# ruirui（10 岁）定制化 AI 使用需求——记录与分析调研

**性质**：面向单一未成年儿童用户的专项需求调研文档，供家长/PO 评估之用。
**范围**：**只记录需求 + 深度分析调研**，不涉及功能设计与开发。
**日期**：2026-07-28
**对象**：ruirui，10 岁，happy-family 家庭共享工具链用户。

> 本文是通用研究《[年龄分级（幼童/儿童/成人）功能设计](./age-tiering-design.md)》的**专项化落地**：
> 把该文"儿童 6–12 档"的通用结论，下沉到 ruirui 这一具体儿童用户 + 三条具体需求上。
> 通用的"分级依据/维度矩阵"不在此重写，直接引用；本文只做"儿童档 + 三需求"的具体化分析。

## 第一部分 · 需求忠实记录

以下为家长（用户）提出需求的原始简报，尽量保留原话，仅做结构整理。

### 1.1 初衷与对象

- **来源**：happy-family 是给家庭成员共享的工具链，其中包含未成年儿童 **ruirui（10 岁）**。
- **总目标**：**有倾向性地引导 ruirui 使用，发掘并放大其中宝贵的灵感，拓展其能力边界。**

### 1.2 ruirui 的用户特征（家长观察）

- **不可能记住 slash command**（无法依赖需要记忆的命令式交互）。
- **语言的顺畅性和逻辑性不如成人**。
- **未必有明确使用目的，但交流中能感觉到火花**（灵感是零散、非结构化的）。

### 1.3 交付 / 交互形态要求

- **更多用 HTML 图形化、动画形式**显示过程和结果。
- **尽量少用 md、表格、chart**（数据罗列式、文本密集式的呈现不适合）。

> ⚠️ 说明：此条是对**给 ruirui 的产品交互体验**的要求，**不是**对本研究文档排版的要求。本文按常规研究文档撰写。

### 1.4 定制需求 1——编程（Python）

- ruirui **对编程感兴趣**。
- 需**针对其年龄特征构建 Python 课程**。
- 需要**手动实践过程**（动手，而非旁观）。
- **更多图形化直观展示，而非罗列数据**。

### 1.5 定制需求 2——游戏与创作

- ruirui **喜欢玩游戏，含桌游**。
- 对**故事性、游戏性、成长和反馈体系**感兴趣，**但不成系统**（兴趣真实但零散）。
- 需引导培养三种能力：**讲故事能力、世界体系设定能力、game 点（玩法机制）设计能力**。
- 需**按其模糊描述产出 PoC**（把孩子说不清的想法变成一个能玩/能看的小样）。

### 1.6 定制需求 3——家长定期反馈

- 作为家长需**定期收到反馈**，具体三问：
  - 有何**成长闪光点**；
  - 有何**不足应加强**；
  - 有何**问题要注意**。

### 1.7 范围边界

- 本轮**只记录需求 + 深入分析调研形成文档**，**不必涉及设计与开发**。

## 第二部分 · 深度分析调研

### 2.1 定位：ruirui 属"儿童 6–12"档

按框架文档 §2 的分档，10 岁的 ruirui 落在**儿童档（6–12）**，发展锚点为：学龄、识字发展中、
**具体运算认知**（能逻辑推理但依赖具体情境）、规则意识形成。这直接解释了家长观察到的三个特征，
也框定了引导策略的边界：

| 家长观察（§1.2） | 儿童档发展锚点解释 | 对引导策略的约束 |
|---|---|---|
| 记不住 slash command | 规则/符号记忆负荷高，学龄儿童工作记忆有限 | 交互必须**免记忆**：自然语言驱动、可视化选择，而非命令式 |
| 语言顺畅性/逻辑性不如成人 | 语言与形式逻辑仍在发展（未达形式运算期） | AI 须能从**模糊、不完整的表达**中善意重构意图（§2.4） |
| 无明确目的但有火花 | 具体运算期靠**具体情境**触发思维，抽象目标设定弱 | 引导重心是**捕捉并放大灵感**，而非要求先立目标 |

框架 §4 的七维差异中，与本任务最相关的四维取值（直接引用儿童档）：

- **输入/输出模态**（§4.1）：简化文字 + 图文混合 → 呼应 §1.3 "HTML 图形化/动画优先"。
- **认知/语言复杂度**（§4.3）：**有脚手架的简单解释、循序渐进、给具体例子** → 三条需求的共同方法论内核。
- **家长监护**（§4.4）：**家长仪表盘 + 使用报告** → 正是需求 3 的落点。
- **视觉/防沉迷**（§4.7）：成就/进度激励，但不制造 FOMO → 约束需求 2 的"反馈体系"设计不得滑向沉迷诱导。

一条贯穿性方法论（对 AI 产品，框架 §6）：分级重心从"界面"前移到"**模型行为的约束层**"——
对 ruirui 而言，关键不在做一个儿童版 UI，而在**通过系统提示把 AI 调成一个"儿童教育者人格"**：
循序渐进、可解释"为什么"、从模糊输入善意重构、鼓励为主。

---

### 2.2 需求 1 分析——面向 10 岁的 Python 教学法

**外部调研结论（儿童编程教育共识）：**

1. **Scratch→Python 的过渡时机，10 岁正当时。** 主流少儿编程教育一致认为：block coding（Scratch）
   先教会"计算思维"（变量/循环/条件/函数）而不被语法拖累；**约 10–11 岁**多数孩子已能承接文本式 Python。
   切换信号是"Scratch 概念的掌握度"，不是年龄本身——需先确认 ruirui 的 block coding 基础。
   若尚无 Scratch 基础，宜先补一段图形化过渡，而非直接上纯文本。

2. **保留"即时可视反馈"是维持兴趣的关键**（直接呼应 §1.4"图形化直观而非罗列数据"）。
   具体载体：
   - **`turtle` 模块**：键入代码即在屏幕上画图，把 Scratch 的"即时可见"迁移到文本代码，且让 debug 直观。
   - **`pygame`**：做小游戏（与需求 2 天然衔接）。
   - **`tkinter`**：做简单图形界面。
   共同点：**代码要"看得见输出"**，避免纯 `print` 数据罗列。

3. **"先基础，立刻进真实项目"** 的教学节奏：讲清变量/循环/条件后，**马上进入一个真实小项目**——
   项目比抽象讲解更能教会概念，也持续给正反馈。

**锚定到 ruirui：**
- 契合点：需求 1 明确要"手动实践 + 图形化直观"，与调研的"hands-on + 可视输出"完全一致。
- 关键前提（待家长确认）：**ruirui 是否有 Scratch/图形化编程基础**，决定起点是"过渡"还是"补图形化前置"。
- 与框架 §4.3 的映射：Python 课程须是**脚手架式**——每步只引入一个具体概念 + 即时可见的成果，而非成人式知识密度。
- 反模式提醒（框架 §7）：不要把课程做成"数据/概念罗列"，那正是家长要避免的呈现方式。

---

### 2.3 需求 2 分析——叙事/世界观/玩法设计能力培养

**外部调研结论（儿童叙事与游戏设计教育）：**

1. **9–10 岁是"游戏好奇心遇上计划能力"的黄金起点。** 研究表明约 9 岁起儿童能理解**因果系统**、
   遵循一份"设计简报（design brief）"、并在不需成人时刻介入下使用 Scratch / Roblox Studio 类工具。
   ruirui 的 10 岁正落在这个窗口。

2. **游戏设计天然是"四合一"能力训练**：**逻辑 + 关卡设计 + 叙事 + 创意**四种能力在一个孩子已经热爱的
   载体里同时得到锻炼——正好覆盖家长要培养的"讲故事 / 世界体系设定 / game 点设计"三项。

3. **叙事驱动设计（narrative-driven design）**：叙事的作用是"给游戏以意义"——先构建角色、目标、
   世界，再让玩法承载故事。学术界已有面向 **8–14 岁**的交互式故事创作工具（在 3D 游戏媒介里创作可供同伴参与的
   互动故事）与**参与式游戏设计**实证研究，证明这个年龄段能产出真实的创作成果。

4. **从"模糊描述"到成品的引导法**：给孩子一份轻量"设计简报"框架（角色是谁 / 想要什么 / 世界什么样 /
   玩起来怎么赢），用**引导式提问**逐步把零散灵感结构化——这与需求 §1.5"按模糊描述产出 PoC"精确对应。

**锚定到 ruirui：**
- 契合点：ruirui"喜欢游戏含桌游、对故事性/成长反馈体系感兴趣但不成系统"——调研的"设计简报 + 引导式提问"
  正是把"不成系统"结构化的手段。**桌游背景是优势**：桌游规则的显式性有利于理解"玩法机制（game 点）"。
- AI 的角色（结合框架 §6 "教育者口吻 + 可解释"）：AI 不替孩子想，而是**用提问把火花挖出来**，
  再据其模糊描述**快速产出一个可玩/可看的 PoC**（呼应 §1.3 HTML/动画形态），让孩子看到"我的想法变成了东西"。
- 与需求 1 的协同：Python 项目（pygame）与游戏设计可合流——**设计→实现**闭环，一举覆盖两条需求。
- 反模式提醒（框架 §4.7 / §7）："成长和反馈体系"要服务于**创作成就感**，不得滑向 FOMO/连续登录压力等诱导式设计。

---

### 2.4 需求 3 分析——家长定期反馈（形成性评估）

**外部调研结论（形成性评估 + AI 亲子辅导）：**

1. **家长要的正是"形成性评估（formative assessment）"**，而非"总结性评估（summative）"。
   形成性评估在学习**过程中**持续进行，目的是**监测学习、给出可帮助识别长处与短板的持续反馈**——
   与需求 §1.6 三问（闪光点 / 应加强的不足 / 要注意的问题）逐一对应：

   | 家长三问 | 形成性评估对应概念 |
   |---|---|
   | 成长闪光点 | strengths / 成长与进步证据（growth evidence） |
   | 不足应加强 | areas that need work / next steps |
   | 问题要注意 | 风险信号（安全、使用模式、情绪等观察） |

2. **好的反馈形态是"叙事式档案（portfolio）"而非分数**：轶事记录（anecdotal notes）+ 作品样例
   （孩子做出的项目/故事）+ 观察清单，构成孩子发展的多维叙事。对 ruirui，这意味着反馈应**附上她的实际产出**
   （画的 turtle 图、做的小游戏、编的故事），让家长看到"技能在行动中"。

3. **AI 中介的亲子辅导已有前沿探索**：检索到 arXiv 论文 **ParaTutor**（LLM 中介、**角色分离**的实时亲子
   辅导脚手架界面）——其思路是把"孩子的学习界面"与"家长的观察/介入界面"分离，AI 在中间做脚手架。
   这为需求 3"家长侧定期反馈"提供了一个可参照的角色分离范式：**孩子端专注创作，家长端定期收到 AI 汇总的成长叙事。**

4. **反馈要"面向成长"而非评判**：形成性反馈应以成长和改进的精神给出，帮助学习者看到自己理解到哪、
   还缺什么、如何深化——语气基调与框架 §6"教育者口吻、可解释、鼓励为主"一致。

**锚定到 ruirui：**
- 契合点：需求 3 与框架 §4.4"家长仪表盘 + 使用报告"是同一落点；本条把它具体化为**周期性的形成性评估叙事**。
- 数据来源：反馈内容应从 ruirui 与 AI 的真实交互 + 产出物中提炼，而非另设测验（避免给孩子加评判压力）。
- 隐私边界（框架 §4.6 / §3.2）：家长可见是正当监护，但仍须遵循**数据最小化**——反馈服务于引导，
  不做超出监护必要的行为画像。
- 与总目标呼应（§1.1）："放大灵感、拓展能力边界"需要反馈闭环来判断"哪束火花值得加柴"——
  反馈机制是整个引导系统的**度量与校准环**。

---

### 2.5 三需求的系统性观察

三条需求并非孤立，而是一个**引导闭环**：

```
灵感(火花) ──引导式提问──▶ 结构化(设计简报/课程步骤)
   ▲                                   │
   │                                   ▼
形成性反馈 ◀──家长侧汇总──  动手产出(Python可视化 / 游戏PoC)
```

- **需求 1（Python）** 与 **需求 2（游戏设计）** 在实现层天然合流（pygame：设计→编码→可玩成品）。
- **需求 3（反馈）** 是这个闭环的**度量环**：从产出中提炼形成性评估，反过来指导下一轮引导方向。
- 贯穿全局的 AI 人格（框架 §6 儿童档）：**免记忆交互、从模糊输入善意重构意图、脚手架式循序渐进、
  可视化优先、鼓励为主、反馈面向成长**。
- 贯穿全局的红线（框架 §7）：**不做诱导式沉迷设计、数据最小化、不确定从严**。

---

### 2.6 待家长/PO 确认的关键前提（供下一步用）

本文只记录与调研，不做设计。但调研中浮现出若干**会实质影响后续设计**的未知项，先行列出：

1. **ruirui 的编程起点**：是否已有 Scratch/图形化编程基础？决定 Python 路径是"直接过渡"还是"先补图形化前置"。
2. **反馈周期**：家长期望的"定期"是周报 / 双周 / 月度？影响形成性评估的采集与汇总节奏。
3. **交互载体的技术形态**：§1.3 的"HTML 图形化/动画"是指在 Happy App 内渲染，还是产出可独立打开的 HTML 页面？
   （属设计问题，此处仅登记，不展开。）
4. **家长在场程度**：儿童档默认"家长仪表盘 + 部分自主"（框架 §4.4），ruirui 的自主边界由家长设定。
